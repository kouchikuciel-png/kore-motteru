# kore-motteru

家庭の所有物と購入予定を重ねて、重複を「禁止せず警告」する共有状態アプリの初号機。

## 目標

2026-10-06 に新井くんが実生活で使い始められる状態にする。

初号機の中心ユースケースは絵本。

- 家主が持っている本を登録する
- 祖父母など第三者が所有リストを見る
- バーコードで所有・購入予定を確認する
- 重複していても購入は禁止しない
- 「重複しています。それでも買いますか？」と判断を人に返す
- 複数人の購入予定をレイヤーとして重ねる

## 最新方針

利用者の役割を二つに分ける。

- **オーナーモード**: 家庭在庫を作る側。新規登録と既存在庫への数量追加ができる。
- **ゲストモード**: 家庭在庫を参照する側。所有確認、購入予定、「渡した」の記録ができる。

OWNERトークンとSHOPトークンは分離したまま維持し、見た目だけのモード切替にはしない。
ゲストから在庫の削除・減算やオーナー権限への昇格はできない。
ゲストが「渡した」を押しても在庫は直接増えず、オーナーの「受け取った」で初めて在庫へ反映する。
ゲストの呼ばれ方（例: じいじ / ばあば）を購入者・贈り主の来歴として残し、来歴表示はオーナーがON/OFFできる。

### レイヤー実証

同一コードで以下を実機確認済み。

- owned_quantity = 1
- planned_quantity = 2
- さらに数量2を購入予定へ追加
- planned_quantity = 4 へ更新

よって「重複は検知するが、禁止しない」モデルはGREEN。

## 家主登録ライン

実機試験で以下を確認した。

- ISBN文字認識から新規登録できる
- 同じISBNをバーコードで読むと既存品として検知できる
- 数量を指定して登録・追加するUIへ合流する
- 日本の書籍の2段バーコードでは、有効なISBN側を優先し `192...` 側を本の識別子として保存しない
- 旧ISBN-10印字をISBN-13へ変換する互換層を持つ
- 書誌情報としてタイトル・著者を表示できる
- 表紙取得は実機で少なくとも1冊の表示成功を確認済み

表紙については1冊の成功だけで安定GREENにはせず、複数冊で再現できた時点で固定する。
失敗時だけ診断UIを表示し、成功時は通常UIに診断情報を出さない。

## 家主登録の受入ゲート

### A. 新規本を複数冊まとめて登録

1. 未登録ISBNを読む
2. 数量UIが1で表示される
3. `＋` で3にする
4. 登録する
5. 所有数量が `×3` になる

### B. 同じ本を追加

1. Aと同じISBNをもう一度読む
2. 「同じものを登録しますか？」と表示される
3. 現在の所有数量を表示する
4. 追加数量を2にして確定する
5. 所有数量が正しく加算される

### C. 日本の書籍2段バーコード

例:

- ISBN側: `9784058008096`
- 価格・分類側: `1920037017002`

同じ画面に2本見えても `1920037017002` は登録候補にせず、ISBN側だけを採用する。

### D. ISBN印字OCR

例: `ISBN978-4-19-862573-3`

- ISBN文字を自動認識
- `9784198625733` へ正規化
- ISBNチェック桁を通過
- バーコード読取と同じ数量UIを表示
- 指定数量で登録できる

### E. 表紙

- 複数の既知本で実機表示される
- 表紙が無い・取得失敗でも登録を続行できる
- 失敗時だけ「表紙診断を見る」が表示される

A〜Eを回帰テストで維持できれば「本の家主登録ライン 安定GREEN」。

## 次工程

初版前に実機で次を一周確認する。

`読む → 登録 → 一覧 → 再読取 → 数量追加`

`ゲスト名 → 購入予定 → 渡した → 受け取り待ち → 受け取った → 在庫 → 来歴表示`

受け取り待ちと同じISBNをオーナーが読んだ場合は、
「受け取った / この分はもう登録済み / 別の1冊として追加する」を選び、同じ出来事の二重計上を避ける。

その後は、バーコード以外の確認入口（商品名検索・スクショ・表紙撮影）と、
シリーズ / スピンオフ / 未所持巻などの「意味のある穴」の可視化へ進む。

## セキュリティ原則

- 生の共有トークンはDBへ保存しない
- DBにはSHA-256ハッシュだけ保存
- OWNERとSHOPを分離
- ブラウザからテーブルを直接読まない
- SECURITY DEFINER RPC 経由のみ
- 商品→所有者の逆引きAPIを作らない
- 家庭IDや家庭の全データを第三者へ直接公開しない

## データ設計の原則

「あとから再現できない事実は、発生時に記録する」。

主なイベント:

- REGISTER
- CHECK_MATCH
- CHECK_NOT_FOUND
- SCAN_FAILED
- DELETE

家主が数量を追加した場合も `REGISTER` として記録し、metadata に追加数量と更新前後の数量を残す。
