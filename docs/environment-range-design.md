# 環境レンジ設計原則

機能を考える時は「理想条件で動くか」だけを見ない。
**最高の環境と最低の環境、最高の結果と最低の結果を先に置き、その間のどこまでを製品が拾うかを決める。**

## 4点を最初に定義する

1. **最高の環境（Emax）**
   - 入力に必要な現物・情報が揃っている
   - 通信、カメラ等の端末機能が使える
   - ユーザーの手間が最小で、判定材料が最も多い

2. **最低の環境（Emin）**
   - 現物がない
   - 通信がない
   - 名前や識別番号が分からない
   - 写真や履歴などの手掛かりも少ない

3. **最高の結果（Rmax）**
   - 正確に特定できる
   - 追加確認がほぼ不要
   - 目的の操作まで短く到達できる

4. **最低の結果（Rmin）**
   - 特定できない、または安全に断定できない
   - ただし誤った結果を確定しない
   - 可能なら入力を一時保存し、後で復旧できる経路を残す

## 設計手順

各機能について次の順に考える。

1. Emaxなら最短で何ができるか
2. 条件を1つずつ失った時の代替手段は何か
3. Eminでも安全に提供できる最低限は何か
4. どこから先は「できない」と明示すべきか
5. どの段階で外部API・AI・人間確認などの追加コストが発生するか
6. その追加価値のどこを無料範囲にし、どこを有料価値にするか

**悪い環境のユーザーを罰するために課金するのではなく、曖昧な状況を解決するための追加計算・自動化・大量処理など、追加価値に対して課金する。**

## kore-motteru での例：1冊の在庫確認

| 環境 | 入力 | 方法 | 確度/コストの考え方 |
| --- | --- | --- | --- |
| 最良 | 本が目の前、通信あり、カメラ可 | 978/979バーコード | 高確度・低コスト。基本導線 |
| 良 | 表紙が見える/画像がある、通信あり | 表紙認識→書誌候補→本人確認 | AI/画像認識コストが増える |
| 中 | 本はないがタイトルが分かる、通信あり | タイトル検索→候補選択 | 低〜中コスト。同名・版違いは人間確認 |
| 弱 | タイトル断片・著者・特徴しか分からない | あいまい検索/AI候補探索 | 計算量と曖昧さが増える。プレミアム候補になり得る |
| 悪 | 通信なしだが家庭在庫を端末に保持 | ローカル在庫内だけ検索 | 外部書誌は使えない。分かる範囲だけ返す |
| 最悪 | 通信なし・本なし・タイトル不明・手掛かりほぼなし | 特定しない | 誤断定しない。可能ならメモ等を残し、通信/情報回復後に再開 |

この表は固定仕様ではない。PoCや実利用でコスト・精度を測り、支援する範囲を決める。

## 課金境界の考え方

課金を先に決めて機能を削らない。
まず環境レンジを作り、各段階の
- 利用頻度
- ユーザーが得る価値
- API/AI等の変動費
- 誤判定リスク
- 人間の確認負荷
を測る。

その上で、たとえば
- 基本のバーコード/タイトル確認は無料
- AIによる曖昧検索
- 本棚写真からの大量一括認識
- 大量処理や高度な提案
など、**追加の計算と省力化が大きい場所**を有料候補として検討する。

## AI/開発時の問い

新しい仕様を提案・実装する前に、最低限これを問う。

> この機能の最高の環境と最低の環境は何か？
>
> 最高の結果と最低の結果は何か？
>
> 条件が悪化した時、どこまで別ルートで拾えるか？
>
> どこからは安全に「分からない」と言うべきか？
>
> 追加コストが発生する地点と、ユーザー価値が増える地点はどこか？

一本道の「正常系 / エラー」ではなく、**環境のグラデーションに対して段階的に能力を落とす**ことを基本とする。
