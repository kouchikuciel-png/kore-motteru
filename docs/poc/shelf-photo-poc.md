# 本棚写真から既存在庫を起こせるか（Issue #44 PoC 報告）

- 実施日: 2026-10-06
- 対象: テストデータ#1（オーナー提供の本棚写真 1 枚、1706×960、部屋全体を写した写真）
- 写真・正解表・解析結果は repo に入れていません（ローカルの一時領域のみ。作業後に破棄）
- 本番コード・Supabase・データには一切触れていません
- 判定: **条件付きGO（次段階の実験へ進む。現状の「部屋全体の写真1枚」での本番化は見送り）**

## 1. 結論（先に）

| 指標 | 結果 |
|---|---|
| 写っている本（人間の目視・概数） | 約 200 冊 |
| 人間が写真から**題名を確実に**読める本 | **4 冊**（ISBN・版まで特定できる本は 0 冊） |
| 人間でもシリーズ名・著者名などの一部だけ読める本 | 約 16 冊 |
| 人間でも判別不能（画像に識別情報が写っていない） | 約 180 冊 |
| 自動: 高確度 | **0**（誤登録 0） |
| 自動: 要確認 | 2（2 件とも正しい本 = 要確認の precision 2/2） |
| 自動: 不明 | 64 |
| 自動: 情報不足（入力画像に識別情報なし） | 67 |
| 人間が読める 4 冊に対する再現率 | 2/4 |
| 処理時間 / 費用 | 約 32 秒（ローカル CPU）/ 0 円 |

この写真 1 枚からは、**人間でも約 200 冊中 4 冊しか題名が確定しない**ため、どんな認識手法でも「既存在庫を起こす」ことはできません。
ボトルネックは認識アルゴリズムより**入力画像の解像度（背表紙 1 冊あたりのピクセル幅）**です。
一方、誤認識を「高確度」に上げない設計（precision 優先）は守れており、取れた候補は 2/2 正しかったため、
**近接写真を前提にした次段階の検証には進む価値がある**、というのが判定理由です。

## 2. 正解表の作り方

- 写真を区画（上段 左/中/右、下段 左/中/右）に分け、8 倍拡大して目視で読み取りました
- 「確実に読める」ものだけを正解とし、推測で題名を補ったものは正解に入れていません
- 読めた題名（4 冊）: 「サファリ」「クリスマスイブのサンタさん」「もこもこもこ」「日本の昔ばなし」
  - いずれも同名・別版・別出版社があり得るため、**ISBN は写真からは確定できない**
- 一部だけ読めるもの（約 16 冊）: 英字シリーズ名の背 ×8、料理本の著者名の背 ×3、面陳列の絵本 1、
  「おやさい…」「くだもの…」系 ×2、「ふしぎ…」、「…うまそうだな」など（題名が確定しないので正解なし扱い）
- 下段左の区画は本ではなく玩具・写真立て（本 0 冊）
- 正解表は Claude による目視なので、**オーナーによる確認を推奨**します（数え間違いの幅: 区画ごとに ±5〜10 冊）

## 3. 比較した認識手法

| # | 手法 | 結果 | 採否 |
|---|---|---|---|
| A | 区画全体を Tesseract（jpn / jpn_vert）で一括 OCR | ノイズのみ。意味のある語 0 | 不採用 |
| B | 背表紙を縦エッジで切り出し → 1 本ずつ OCR | 意味のない文字列が 6 件「要確認」に上がる（誤検出） | 不採用 |
| C | 人手で正確に切り出した背表紙を OCR（上限の確認） | 幅 28px の「サファリ」は安定して読める、20px は部分的、11〜16px は全滅 | 参考値 |
| D | **縦長スライド窓 OCR（28px 窓・10px 間隔・4 倍拡大）＋信頼度 60 以上＋同一文字の繰り返し除去** | 要確認 2 件（2 件とも正しい本）、誤検出 0 | **採用** |
| E | 画像対応 AI（VLM）に写真を渡す | 有料 API キーが必要なため未実施（費用見積りのみ。§6） | 未実施 |
| F | 書誌照合（NDL サーチ / openBD / Open Library / Google Books） | この作業環境からは通信が遮断（403）または無料枠切れ（429）で実行不可 | 未実施（照合部分はスタブ） |

採用した D は `poc/shelf-photo/shelf_poc.py` です。

### 判定区分の決め方（precision 優先）

1. 背表紙幅 10px 未満で文字列が取れない → **情報不足**（入力画像そのものに識別情報がない）
2. 文字列が取れない → **不明**
3. 日本語 3 字以上 / 英単語 4 字以上の意味のある文字列が取れた → **要確認**
4. 書誌照合で ISBN が一意に決まった時だけ → **高確度**（今回は照合が使えないため常に 0）

OCR の文字列だけで「高確度」にすることはしません。誤読（後述）が普通に起きるためです。

## 4. 実測結果（テストデータ#1）

- 背表紙として検出した領域: 133（実際は約 200 冊。うち 18 領域は本のない玩具区画の誤検出）
- 分類: 高確度 0 / 要確認 2 / 不明 64 / 情報不足 67

人間が読める 4 冊ごとの結果:

| 題名（人間の正解） | 背表紙幅 | 自動の結果 | OCR 文字列 |
|---|---|---|---|
| サファリ | 約 30px | 要確認 ✅ | 「ョファリー」 |
| クリスマスイブのサンタさん | 約 22px | 要確認 ✅ | 「リスマスイプの」 |
| もこもこもこ | 約 12px | 情報不足 ❌ | なし |
| 日本の昔ばなし | 約 15px | 不明 ❌ | なし |

### 実用限界の目安

- OCR が読めるのは背表紙幅 **約 20px 以上**、安定するのは **約 28px 以上**
- 人間は 8〜11px でも太い文字の題名なら読めることがある
- この写真では大半の背表紙が 5〜12px で、人間にも OCR にも読めない

## 5. 誤認識の具体例

| 種類 | 例 | 対策 |
|---|---|---|
| 似た字の取り違え | 「サ」→「ョ」（サファリ → ョファリー）、「ブ」→「プ」（イブ → イプ） | 文字列一致で確定させず、必ず書誌照合＋人の確認。評価は 3 字以上の部分一致で行った |
| 先頭・末尾の欠け | 「クリスマスイブ…」の「ク」が欠ける | 部分一致で候補を出す（自動確定しない） |
| 模様・イラストを文字と誤読 | 手法 B で「ーーーー」「一一一」「ミミミ」のような文字列が 6 件上がった | 同じ文字が半分を超える断片を除去、信頼度 60 未満を捨てる |
| 本以外を背表紙と誤検出 | 玩具・写真立ての区画で 18 領域 | 区画の指定と、文字列が取れなければ「不明」止まりにすることで登録には繋がらない |
| 複数の背表紙をまとめて 1 本と検出 | 細い背表紙が並ぶ区画で頻発（検出 133 < 実数約 200） | 近接写真で幅を確保する以外に決定打なし |

いずれも「要確認」より上に行かないため、**誤登録は 0** でした。

## 6. 時間と費用（1 枚あたり）

| 方式 | 時間 | 費用 | 備考 |
|---|---|---|---|
| ローカル OCR（今回の D） | 約 32 秒（コンテナの CPU） | 0 円 | 端末内で実行するなら Tesseract.js 等が必要。スマホではさらに遅い見込み |
| VLM（Claude API、未実施・見積り） | 数秒〜十数秒 | 約 1〜3 円 | 1706×960 で画像約 2,100 トークン＋指示・出力。Sonnet 5.5（入力 $2 / 出力 $10 per 100 万トークン）で 1 枚 $0.01〜0.02 程度。高解像度（長辺 2576px）でも画像約 4,800 トークン |
| 書誌照合 | 1 候補あたり 0.3〜1 秒 | 0 円（無料 API） | アプリ本体と同じく端末（ブラウザ）から呼ぶ想定 |

VLM の費用は公表単価からの概算で、実際の API は呼んでいません（有料 API 契約が必要なため、指示どおり実施していません）。

## 7. プライバシー

- テストデータ#1 には、**本以外に子どもの写真（写真立て）や部屋の様子**が写っていました。本棚写真は家庭内の情報を含むのが普通、と考える必要があります
- EXIF に撮影情報ブロックがあり（今回 GPS タグは見当たらず）。外部へ送る場合は**送信前に EXIF を除去**し、本棚部分だけに切り抜くべきです
- 今回の PoC は写真を外部に送っていません（ローカル OCR のみ）。写真・正解表・解析結果は repo に入れていません
- 本番化して VLM を使う場合の必須条件:
  - 「写真を外部の AI に送ります」と送信前に明示し、同意を得る
  - API キーはフロントエンドに置かず、サーバー側（例: Supabase Edge Function）から呼ぶ
  - 写真は保存しない（処理後に破棄。ログにも残さない）

## 8. kore-motteru への接続点（案）

本番の権限・データの意味は変えずに済む形を想定しています。

1. owner.html に別画面「まとめて取り込み（下書き）」を追加
2. 写真 → 候補リスト（要確認のみ。自動登録はしない）を表示
3. オーナーが 1 件ずつ「これで合ってる」を押すと、既存の本登録経路
   （書誌検索 → `register_household_item_quantity`）に渡す。ISBN が確定しない候補はバーコード読み取りに誘導
4. 下書きは端末内だけに置き、DB には確定分しか入れない

新しい DB テーブル・RPC・権限の変更は不要です。VLM を使う場合だけ、新しいサーバー側処理（Edge Function）と有料 API 契約が必要になり、これは今回の指示の「止めて報告」に当たるため実装していません。

## 9. 判定: 条件付きGO

**本番機能としての「部屋全体の写真 1 枚から在庫を起こす」は見送り**です（人間でも 4/200 冊しか読めない入力では原理的に無理）。
ただし次の条件付きで、**次段階の検証には GO** とします。

1. 入力は**区画ごとの近接写真**（背表紙 1 冊あたり 20px 以上、目安として 1 枚に 15〜25 冊）を前提にする
2. 認識結果はすべて「要確認」止まりで、**人が確認したものだけ登録**する（高確度でも自動登録しない）
3. 書誌照合を端末またはサーバーから実行し、ISBN が一意に決まらない候補はバーコード登録に回す
4. 精度が足りなければ VLM を検討。その際は有料 API 契約・サーバー処理・送信同意が必要になるため、オーナーの判断を仰ぐ

### 次にやる実験（提案）

- 同じ本棚を**区画ごとに近接撮影した写真**（6 枚程度）で同じ PoC を再実行し、要確認の件数と precision を測る
- 書誌照合が通る環境（オーナーの端末のブラウザ等）で、要確認候補 → ISBN の一意化率を測る
- 合意が取れれば、同じ写真で VLM を 1 回だけ試し、ローカル OCR と比較する
